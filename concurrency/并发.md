# 第 1 题：mutex 与数据竞争

## 1. 最终 counter 是否一定为 200000？

不一定。

两个线程同时执行：

```cpp
int counter = 0;

void worker() {
    for (int i = 0; i < 100000; ++i)
        ++counter;
}
```

从直觉上看，两个线程各加 `100000` 次，好像最终应该是 `200000`。但 `++counter` 不是原子操作，两个线程可能同时读写同一个共享变量，导致数据竞争。

在 C++ 语义中，如果多个线程并发访问同一个对象，其中至少一个是写操作，并且没有同步手段，就会产生 data race。data race 属于 undefined behavior，不只是“结果不准”这么简单。

## 2. 为什么 ++counter 不是原子操作？

`++counter` 是一个 read-modify-write 操作，汇编层面通常可以理解为三步：

```asm
mov eax, DWORD PTR [counter]   ; 读 counter 到寄存器
add eax, 1                     ; 寄存器中的值加 1
mov DWORD PTR [counter], eax   ; 写回 counter
```

这三步之间可能被另一个线程插入。

例如：

```text
counter = 0

线程 A: 读取 counter -> 0
线程 B: 读取 counter -> 0
线程 A: 计算 0 + 1，写回 1
线程 B: 计算 0 + 1，写回 1
```

两个线程都执行了一次 `++counter`，但最终 `counter` 只从 `0` 变成了 `1`，这叫丢失更新。

## 3. 从寄存器角度理解多线程并发

每个线程都有自己的执行上下文，包括：

```text
通用寄存器
栈指针
程序计数器
线程栈
```

但这不是说每个线程永久独占一套物理寄存器。更准确地说：

```text
线程运行时，CPU 物理寄存器里装的是当前线程的寄存器状态；
线程被切走时，操作系统保存这份寄存器状态；
线程下次被调度回来时，操作系统再恢复这份状态。
```

所以 `counter` 的竞争不是因为两个线程抢同一个 `eax`，而是因为：

```text
线程 A 把共享内存 counter 读到自己的寄存器
线程 B 也把共享内存 counter 读到自己的寄存器
两个线程分别计算
最后都写回同一块共享内存
```

寄存器状态是线程私有的，真正共享的是全局变量、堆内存等进程地址空间中的数据。

## 4. mutex 如何避免竞争？

`mutex` 的作用是保护临界区，让同一时刻只有一个线程能执行被保护的代码。

```cpp
std::mutex mx;
int counter = 0;

void workerWithMutex() {
    for (int i = 0; i < 100000; ++i) {
        std::lock_guard<std::mutex> lock(mx);
        ++counter;
    }
}
```

`std::lock_guard` 大致等价于：

```cpp
mx.lock();
++counter;
mx.unlock();
```

只不过它使用 RAII，在作用域结束时自动释放锁。

加锁后的执行顺序类似：

```text
counter = 0

线程 A: lock 成功
线程 A: 读取 counter -> 0
线程 B: lock 失败，阻塞等待
线程 A: +1，写回 1
线程 A: unlock

线程 B: lock 成功
线程 B: 读取 counter -> 1
线程 B: +1，写回 2
线程 B: unlock
```

所以 mutex 不是让 `++counter` 本身变成一条原子指令，而是让包含 `++counter` 的临界区互斥执行。

## 5. 线程加锁失败后会怎样？

`std::mutex::lock()` 获取失败后，语义上是阻塞。

具体实现通常分两层：

```text
1. 先短暂自旋，在用户态反复尝试获取锁
2. 如果一段时间后仍拿不到锁，进入内核等待，例如 Linux futex
```

进入内核等待后，线程会睡眠或挂起，暂时不占用 CPU。持锁线程释放锁后，操作系统再唤醒等待线程。

需要注意：

```text
被唤醒不等于已经拿到锁；
被唤醒后只是重新参与调度和锁竞争。
```

## 6. mutex 的汇编和底层实现

`std::mutex` 不是一条汇编指令，而是标准库对平台锁机制的封装。

在 Linux 上大致可以理解为：

```text
std::mutex
  -> pthread_mutex_t
    -> CPU 原子指令 + futex 等操作系统等待机制
```

加锁的核心思想是用硬件原子指令抢占锁状态：

```cpp
// 0 表示未加锁，1 表示已加锁
std::atomic<int> state = 0;
```

错误写法是：

```cpp
if (state == 0) {
    state = 1;
}
```

因为两个线程可能同时看到 `state == 0`，然后都认为自己拿到了锁。

正确做法需要原子 compare-and-swap，x86 上可能对应类似：

```asm
lock cmpxchg DWORD PTR [mutex_state], edx
```

它保证：

```text
读取锁状态
判断是否为未加锁
如果未加锁则改成已加锁
```

这整个 read-modify-write 过程对其他核心不可分割。

## 7. 原子操作是怎么保证的？

原子操作主要靠 CPU 硬件保证，不是靠操作系统在调度时不切换线程来保证。

单核上，一条机器指令通常不会被线程调度切到另一条线程指令中间。

但多核场景下，即使当前线程没有被切换，另一个核心也可能正在同时执行另一个线程。因此只靠操作系统调度不够，必须依赖 CPU 的原子指令和缓存一致性协议。

例如 x86 上：

```asm
lock addl $1, [counter]
```

或者：

```asm
lock cmpxchg [addr], reg
```

`lock` 前缀会让 CPU 对目标内存地址所在的 cache line 获得独占修改权，使其他核心对同一 cache line 的冲突修改等待或重试。

现代 CPU 通常不是粗暴地锁住整个内存总线，而是通过缓存一致性协议，例如 MESI/MOESI 一类机制，让某个核心在修改对应 cache line 时具有独占权限。

所以硬件原子操作依赖：

```text
CPU 原子 read-modify-write 指令
缓存行独占权限
缓存一致性协议
编译器对 atomic 语义的配合
```

## 8. atomic 如何避免竞争？

使用 `std::atomic<int>`：

```cpp
std::atomic<int> counter_atomic{0};

void workerWithAtomic() {
    for (int i = 0; i < 100000; ++i) {
        ++counter_atomic;
    }
}
```

在 x86-64 上，`++counter_atomic` 通常会被编译成类似：

```asm
lock addl $1, counter_atomic(%rip)
```

普通 `int` 的 `++counter` 可能是：

```asm
mov eax, DWORD PTR [counter]
add eax, 1
mov DWORD PTR [counter], eax
```

而 atomic 的 `++counter_atomic` 是一条带 `lock` 前缀的原子加法指令。它直接让“读、加、写”这个过程成为硬件原子操作。

两个线程同时执行：

```asm
lock addl $1, counter_atomic
```

硬件会把它们对同一个内存位置的修改串行化：

```text
counter_atomic = 0

线程 A: lock addl，0 -> 1
线程 B: lock addl，1 -> 2
```

因此不会出现两个线程都读到 `0`，最后都写回 `1` 的丢失更新。

## 9. mutex 和 atomic 的适用场景

`mutex` 适合保护一段临界区，尤其是多个共享变量或复杂逻辑。

典型场景：

```text
保护 vector / map / queue 等容器
同时修改多个变量
多步操作需要保持一致性
需要和 condition_variable 配合
临界区内逻辑较复杂
```

例如：

```cpp
std::mutex m;
std::vector<int> data;

void push(int x) {
    std::lock_guard<std::mutex> lock(m);
    data.push_back(x);
}
```

`atomic` 适合单个变量上的简单原子操作。

典型场景：

```text
计数器
退出标志
简单状态位
引用计数
统计指标
无锁数据结构的底层构件
```

例如：

```cpp
std::atomic<bool> stop{false};

void worker() {
    while (!stop.load()) {
        // do work
    }
}
```

选择规则：

```text
一个变量，一个简单操作：优先考虑 atomic
多个变量，多步逻辑，需要维护不变量：使用 mutex
涉及标准容器的并发访问：通常使用 mutex
需要等待某个条件：mutex + condition_variable
```

不要为了追求无锁而滥用 atomic。atomic 适合表达简单的并发状态；一旦逻辑涉及多个步骤，mutex 往往更清晰、更安全。

## 10. 面试回答模板

可以这样回答：

```text
++counter 不是原子操作，它本质是 read-modify-write，可能被拆成读内存、寄存器加一、写回内存三步。

多个线程同时执行时，可能都读到同一个旧值，然后分别写回相同的新值，导致丢失更新。

在 C++ 中，这种没有同步的并发读写属于 data race，是 undefined behavior。

mutex 通过互斥保护临界区，让同一时刻只有一个线程执行 ++counter，并且 lock/unlock 还提供内存同步语义。

atomic 则让单个变量的读改写操作直接编译成硬件原子指令，例如 x86 的 lock addl，通过缓存一致性协议保证多个核心对同一内存位置的修改被串行化。

mutex 适合保护复杂临界区、多个变量和容器；atomic 适合计数器、标志位等单个变量的简单并发操作。
```
