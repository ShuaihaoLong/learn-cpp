# 第 1 题：mutex 与数据竞争

## 1. 最终 counter 是否一定为 200000？

不一定。

两个线程同时执行：

```cpp
int counter = 0;

void worker() {
    for (int i = 0; i < 100000; ++i)
        ++counter;
}
```

从直觉上看，两个线程各加 `100000` 次，好像最终应该是 `200000`。但 `++counter` 不是原子操作，两个线程可能同时读写同一个共享变量，导致数据竞争。

在 C++ 语义中，如果多个线程并发访问同一个对象，其中至少一个是写操作，并且没有同步手段，就会产生 data race。data race 属于 undefined behavior，不只是“结果不准”这么简单。

## 2. 为什么 ++counter 不是原子操作？

`++counter` 是一个 read-modify-write 操作，汇编层面通常可以理解为三步：

```asm
mov eax, DWORD PTR [counter]   ; 读 counter 到寄存器
add eax, 1                     ; 寄存器中的值加 1
mov DWORD PTR [counter], eax   ; 写回 counter
```

这三步之间可能被另一个线程插入。

例如：

```text
counter = 0

线程 A: 读取 counter -> 0
线程 B: 读取 counter -> 0
线程 A: 计算 0 + 1，写回 1
线程 B: 计算 0 + 1，写回 1
```

两个线程都执行了一次 `++counter`，但最终 `counter` 只从 `0` 变成了 `1`，这叫丢失更新。

## 3. 从寄存器角度理解多线程并发

每个线程都有自己的执行上下文，包括：

```text
通用寄存器
栈指针
程序计数器
线程栈
```

但这不是说每个线程永久独占一套物理寄存器。更准确地说：

```text
线程运行时，CPU 物理寄存器里装的是当前线程的寄存器状态；
线程被切走时，操作系统保存这份寄存器状态；
线程下次被调度回来时，操作系统再恢复这份状态。
```

所以 `counter` 的竞争不是因为两个线程抢同一个 `eax`，而是因为：

```text
线程 A 把共享内存 counter 读到自己的寄存器
线程 B 也把共享内存 counter 读到自己的寄存器
两个线程分别计算
最后都写回同一块共享内存
```

寄存器状态是线程私有的，真正共享的是全局变量、堆内存等进程地址空间中的数据。

## 4. mutex 如何避免竞争？

`mutex` 的作用是保护临界区，让同一时刻只有一个线程能执行被保护的代码。

```cpp
std::mutex mx;
int counter = 0;

void workerWithMutex() {
    for (int i = 0; i < 100000; ++i) {
        std::lock_guard<std::mutex> lock(mx);
        ++counter;
    }
}
```

`std::lock_guard` 大致等价于：

```cpp
mx.lock();
++counter;
mx.unlock();
```

只不过它使用 RAII，在作用域结束时自动释放锁。

加锁后的执行顺序类似：

```text
counter = 0

线程 A: lock 成功
线程 A: 读取 counter -> 0
线程 B: lock 失败，阻塞等待
线程 A: +1，写回 1
线程 A: unlock

线程 B: lock 成功
线程 B: 读取 counter -> 1
线程 B: +1，写回 2
线程 B: unlock
```

所以 mutex 不是让 `++counter` 本身变成一条原子指令，而是让包含 `++counter` 的临界区互斥执行。

## 5. 线程加锁失败后会怎样？

`std::mutex::lock()` 获取失败后，语义上是阻塞。

具体实现通常分两层：

```text
1. 先短暂自旋，在用户态反复尝试获取锁
2. 如果一段时间后仍拿不到锁，进入内核等待，例如 Linux futex
```

进入内核等待后，线程会睡眠或挂起，暂时不占用 CPU。持锁线程释放锁后，操作系统再唤醒等待线程。

需要注意：

```text
被唤醒不等于已经拿到锁；
被唤醒后只是重新参与调度和锁竞争。
```

## 6. mutex 的汇编和底层实现

`std::mutex` 不是一条汇编指令，而是标准库对平台锁机制的封装。

在 Linux 上大致可以理解为：

```text
std::mutex
  -> pthread_mutex_t
    -> CPU 原子指令 + futex 等操作系统等待机制
```

加锁的核心思想是用硬件原子指令抢占锁状态：

```cpp
// 0 表示未加锁，1 表示已加锁
std::atomic<int> state = 0;
```

错误写法是：

```cpp
if (state == 0) {
    state = 1;
}
```

因为两个线程可能同时看到 `state == 0`，然后都认为自己拿到了锁。

正确做法需要原子 compare-and-swap，x86 上可能对应类似：

```asm
lock cmpxchg DWORD PTR [mutex_state], edx
```

它保证：

```text
读取锁状态
判断是否为未加锁
如果未加锁则改成已加锁
```

这整个 read-modify-write 过程对其他核心不可分割。

## 7. 原子操作是怎么保证的？

原子操作主要靠 CPU 硬件保证，不是靠操作系统在调度时不切换线程来保证。

单核上，一条机器指令通常不会被线程调度切到另一条线程指令中间。

但多核场景下，即使当前线程没有被切换，另一个核心也可能正在同时执行另一个线程。因此只靠操作系统调度不够，必须依赖 CPU 的原子指令和缓存一致性协议。

例如 x86 上：

```asm
lock addl $1, [counter]
```

或者：

```asm
lock cmpxchg [addr], reg
```

`lock` 前缀会让 CPU 对目标内存地址所在的 cache line 获得独占修改权，使其他核心对同一 cache line 的冲突修改等待或重试。

现代 CPU 通常不是粗暴地锁住整个内存总线，而是通过缓存一致性协议，例如 MESI/MOESI 一类机制，让某个核心在修改对应 cache line 时具有独占权限。

所以硬件原子操作依赖：

```text
CPU 原子 read-modify-write 指令
缓存行独占权限
缓存一致性协议
编译器对 atomic 语义的配合
```

## 8. atomic 如何避免竞争？

使用 `std::atomic<int>`：

```cpp
std::atomic<int> counter_atomic{0};

void workerWithAtomic() {
    for (int i = 0; i < 100000; ++i) {
        ++counter_atomic;
    }
}
```

在 x86-64 上，`++counter_atomic` 通常会被编译成类似：

```asm
lock addl $1, counter_atomic(%rip)
```

普通 `int` 的 `++counter` 可能是：

```asm
mov eax, DWORD PTR [counter]
add eax, 1
mov DWORD PTR [counter], eax
```

而 atomic 的 `++counter_atomic` 是一条带 `lock` 前缀的原子加法指令。它直接让“读、加、写”这个过程成为硬件原子操作。

两个线程同时执行：

```asm
lock addl $1, counter_atomic
```

硬件会把它们对同一个内存位置的修改串行化：

```text
counter_atomic = 0

线程 A: lock addl，0 -> 1
线程 B: lock addl，1 -> 2
```

因此不会出现两个线程都读到 `0`，最后都写回 `1` 的丢失更新。

## 9. mutex 和 atomic 的适用场景

`mutex` 适合保护一段临界区，尤其是多个共享变量或复杂逻辑。

典型场景：

```text
保护 vector / map / queue 等容器
同时修改多个变量
多步操作需要保持一致性
需要和 condition_variable 配合
临界区内逻辑较复杂
```

例如：

```cpp
std::mutex m;
std::vector<int> data;

void push(int x) {
    std::lock_guard<std::mutex> lock(m);
    data.push_back(x);
}
```

`atomic` 适合单个变量上的简单原子操作。

典型场景：

```text
计数器
退出标志
简单状态位
引用计数
统计指标
无锁数据结构的底层构件
```

例如：

```cpp
std::atomic<bool> stop{false};

void worker() {
    while (!stop.load()) {
        // do work
    }
}
```

选择规则：

```text
一个变量，一个简单操作：优先考虑 atomic
多个变量，多步逻辑，需要维护不变量：使用 mutex
涉及标准容器的并发访问：通常使用 mutex
需要等待某个条件：mutex + condition_variable
```

不要为了追求无锁而滥用 atomic。atomic 适合表达简单的并发状态；一旦逻辑涉及多个步骤，mutex 往往更清晰、更安全。

## 10. 面试回答模板

可以这样回答：

```text
++counter 不是原子操作，它本质是 read-modify-write，可能被拆成读内存、寄存器加一、写回内存三步。

多个线程同时执行时，可能都读到同一个旧值，然后分别写回相同的新值，导致丢失更新。

在 C++ 中，这种没有同步的并发读写属于 data race，是 undefined behavior。

mutex 通过互斥保护临界区，让同一时刻只有一个线程执行 ++counter，并且 lock/unlock 还提供内存同步语义。

atomic 则让单个变量的读改写操作直接编译成硬件原子指令，例如 x86 的 lock addl，通过缓存一致性协议保证多个核心对同一内存位置的修改被串行化。

mutex 适合保护复杂临界区、多个变量和容器；atomic 适合计数器、标志位等单个变量的简单并发操作。
```

# 第 2 题：RAII 与锁管理

## 1. 裸 lock/unlock 有什么风险？

下面这种写法有异常安全问题：

```cpp
mutex.lock();
doSomething();
mutex.unlock();
```

如果 `doSomething()` 正常返回，代码看起来没问题：

```text
lock 成功
执行 doSomething
unlock 释放锁
```

但如果 `doSomething()` 中途抛出异常，控制流会直接跳出当前函数，后面的 `mutex.unlock()` 不会执行。

结果就是：

```text
当前线程已经持有 mutex
异常导致函数提前退出
mutex 没有被释放
其他线程之后再 lock 这个 mutex 时会一直阻塞
程序可能卡死
```

这类问题本质是：手动资源管理依赖“代码一定走到释放语句”，但异常、提前 `return`、分支跳转都会破坏这个假设。

锁也是一种资源。拿锁是获取资源，解锁是释放资源。

## 2. RAII 如何解决锁管理问题？

RAII 是 Resource Acquisition Is Initialization，意思是：

```text
对象构造时获取资源
对象析构时释放资源
```

锁管理里，RAII 的典型写法是：

```cpp
void safeWork() {
    std::lock_guard<std::mutex> lock(mutex);
    doSomething();
}
```

`std::lock_guard` 构造时调用 `mutex.lock()`，析构时调用 `mutex.unlock()`。

即使 `doSomething()` 抛异常，栈展开时也会自动析构局部对象：

```text
进入 safeWork
构造 lock_guard，自动 lock
doSomething 抛异常
开始栈展开
lock_guard 析构，自动 unlock
异常继续向外传播
```

所以 RAII 的价值是：把锁释放绑定到对象生命周期，而不是依赖程序员手动写 `unlock()`。

面试中可以强调：

```text
RAII 不只是代码风格问题，而是 C++ 中实现异常安全的核心机制。
```

## 3. std::lock_guard

`std::lock_guard` 是最简单的锁包装器。

特点：

```text
构造时加锁
析构时解锁
不可手动 unlock
不可重新 lock
不可移动
开销小，语义简单
```

适合普通临界区：

```cpp
std::mutex m;
int value = 0;

void add() {
    std::lock_guard<std::mutex> lock(m);
    ++value;
}
```

如果只是进入作用域加锁、离开作用域解锁，优先使用 `std::lock_guard`。

## 4. std::unique_lock

`std::unique_lock` 比 `lock_guard` 更灵活。

特点：

```text
构造时可以立即加锁，也可以延迟加锁
可以手动 unlock
可以手动重新 lock
可以移动
可以配合 condition_variable
开销比 lock_guard 略高，因为它需要记录更多状态
```

示例：

```cpp
std::unique_lock<std::mutex> lock(m);
doSomethingWithLock();

lock.unlock();
doSomethingWithoutLock();

lock.lock();
doMoreWithLock();
```

`unique_lock` 适合需要灵活控制锁生命周期的场景。

常见用法包括：

```text
condition_variable 等待
临界区中途需要提前释放锁
需要转移锁所有权
需要延迟加锁
```

延迟加锁示例：

```cpp
std::unique_lock<std::mutex> lock(m, std::defer_lock);
// 做一些准备工作
lock.lock();
```

## 5. std::scoped_lock

`std::scoped_lock` 是 C++17 引入的锁包装器，适合同时锁多个 mutex。

单个 mutex 时也可以用：

```cpp
std::scoped_lock lock(m);
```

多个 mutex 时更有价值：

```cpp
std::mutex m1;
std::mutex m2;

void work() {
    std::scoped_lock lock(m1, m2);
    // 同时持有 m1 和 m2
}
```

它内部会使用类似 `std::lock` 的死锁避免算法，降低多个 mutex 同时加锁时因为加锁顺序不同导致死锁的风险。

典型死锁场景：

```text
线程 A: lock m1
线程 A: 等待 m2

线程 B: lock m2
线程 B: 等待 m1
```

此时 A 等 B，B 等 A，两个线程都无法继续。

`std::scoped_lock(m1, m2)` 的意义是：用标准库提供的方式一次性获取多个锁，避免手写多个 `lock()` 带来的顺序问题。

## 6. lock_guard、unique_lock、scoped_lock 的区别

可以这样对比：

```text
lock_guard:
  最简单，构造加锁，析构解锁，不能手动解锁。
  适合普通临界区。

unique_lock:
  更灵活，可以手动 lock/unlock，可以延迟加锁，可以移动。
  适合 condition_variable 和复杂锁生命周期。

scoped_lock:
  适合一次性锁住一个或多个 mutex。
  多个 mutex 时能降低死锁风险。
```

选择规则：

```text
普通临界区：lock_guard
需要配合 condition_variable：unique_lock
需要提前解锁或重新加锁：unique_lock
需要同时锁多个 mutex：scoped_lock
```

## 7. 为什么 condition_variable 通常使用 unique_lock？

`condition_variable::wait()` 需要在等待过程中临时释放 mutex，并在被唤醒后重新获取 mutex。

典型写法：

```cpp
std::mutex m;
std::condition_variable cv;
bool ready = false;

void waitThread() {
    std::unique_lock<std::mutex> lock(m);
    cv.wait(lock, [] { return ready; });
}
```

`cv.wait(lock, pred)` 内部大致逻辑是：

```text
检查 pred 是否为 true
如果为 false：
  原子地释放 mutex，并让当前线程进入等待
被 notify 唤醒后：
  重新获取 mutex
  再次检查 pred
```

这里的关键是：`wait()` 必须能够操作传进来的锁对象，让它暂时 `unlock()`，醒来后再 `lock()`。

`lock_guard` 不支持手动解锁和重新加锁，因此不能满足 `condition_variable` 的需求。

所以 `condition_variable` 使用 `unique_lock`，不是因为它更高级，而是因为等待语义需要可解锁、可重新加锁的锁对象。

## 8. 多个 mutex 同时加锁时，如何降低死锁风险？

第一种方法：固定加锁顺序。

所有线程都按同一个顺序加锁：

```cpp
std::lock_guard<std::mutex> lock1(m1);
std::lock_guard<std::mutex> lock2(m2);
```

只要整个项目中都遵守相同顺序，例如永远先锁 `m1` 再锁 `m2`，就可以破坏死锁的循环等待条件。

第二种方法：使用 `std::scoped_lock`。

```cpp
std::scoped_lock lock(m1, m2);
```

它适合一次性获取多个 mutex，比手写连续 `lock()` 更安全。

第三种方法：使用 `std::lock` 搭配 `adopt_lock`。

```cpp
std::lock(m1, m2);
std::lock_guard<std::mutex> lock1(m1, std::adopt_lock);
std::lock_guard<std::mutex> lock2(m2, std::adopt_lock);
```

`std::lock(m1, m2)` 会负责以避免死锁的方式获取多个锁；`std::adopt_lock` 表示这个 mutex 已经被当前线程锁住，`lock_guard` 只负责后续析构时释放。

C++17 以后更推荐直接使用：

```cpp
std::scoped_lock lock(m1, m2);
```

第四种方法：缩小临界区。

不要在持锁时做耗时操作，例如：

```text
网络 I/O
磁盘 I/O
复杂计算
调用未知外部回调
```

持锁时间越长，其他线程等待时间越长，死锁和性能问题越容易出现。

## 9. 面试回答模板

可以这样回答：

```text
裸写 mutex.lock() 和 mutex.unlock() 的风险是异常安全。如果 lock 之后的代码抛异常，unlock 不会执行，mutex 会一直保持加锁状态，其他线程之后获取这把锁时可能永久阻塞。

C++ 中应该使用 RAII 管理锁，也就是让锁包装器在构造时加锁，在析构时自动解锁。这样即使发生异常，栈展开时也会析构局部对象，从而释放锁。

lock_guard 是最简单的 RAII 锁，适合普通临界区；unique_lock 更灵活，支持手动 unlock、重新 lock、延迟加锁和移动，因此常用于 condition_variable；scoped_lock 适合同时锁一个或多个 mutex，多个 mutex 时可以降低死锁风险。

condition_variable 通常使用 unique_lock，是因为 wait 过程中需要临时释放 mutex，让其他线程有机会修改条件并 notify；被唤醒后又要重新获取 mutex。lock_guard 不支持这种解锁和重新加锁的操作。

多个 mutex 同时加锁时，可以通过固定加锁顺序、std::scoped_lock、std::lock + adopt_lock、缩小临界区等方式降低死锁风险。
```

# 第 3 题：condition_variable 与 BlockingQueue

## 1. 当前代码检查

当前 `question3.cpp` 的核心实现是：

```cpp
template <typename T>
class BlockingQueue {
public:
    BlockingQueue () : running_(true) {}

    void push(T value) {
        std::lock_guard<std::mutex> lock(mutex_);
        queue_.push(value);
        std::cout << "queue push " << value << "\n";
        cv_.notify_all();
    }

    std::optional<T> pop() {
        std::unique_lock<std::mutex> lock(mutex_);
        cv_.wait(lock, [this] () {
            return !queue_.empty() || !running_;
        });
        if (queue_.empty()) {
            return std::nullopt;
        }
        T res = queue_.front();
        queue_.pop();
        std::cout << "queue pop " << res << "\n";
        return res;
    }

    void stop() {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            running_ = false;
        }
        cv_.notify_all();
    }

private:
    std::queue<T> queue_;
    std::mutex mutex_;
    std::condition_variable cv_;
    bool running_{false};
};
```

整体方向是正确的：

```text
queue_ 由 mutex_ 保护
running_ 也由 mutex_ 保护
pop 使用 unique_lock 配合 condition_variable
wait 使用谓词处理虚假唤醒
stop 后 notify_all 唤醒所有等待线程
pop 使用 optional 表达“停止且无数据”
```

其中最关键的是 `pop()` 的等待条件：

```cpp
return !queue_.empty() || !running_;
```

它表示：

```text
队列不为空：消费者可以继续 pop
队列为空但已经 stop：消费者也要醒来退出
```

这个条件比之前的：

```cpp
return !queue_.empty() && !running_;
```

更合理。后者表示“队列非空并且已经停止才继续”，会导致生产过程中即使队列里有数据，消费者也一直不消费。

## 2. 一个 BlockingQueue 至少要解决什么问题？

BlockingQueue 的目标是让多个生产者、多个消费者安全地共享一个队列。

它至少要解决：

```text
push 时互斥修改队列
pop 时队列为空要阻塞等待
push 后要唤醒等待中的消费者
stop 后要唤醒所有消费者
wait 要能处理虚假唤醒
stop 后要定义剩余元素如何处理
```

你的当前语义是：

```text
stop 后，如果队列还有数据，消费者继续取出剩余元素
stop 后，如果队列为空，pop 返回 std::nullopt
```

这是一个清晰且常见的 shutdown 语义。

## 3. 为什么 condition_variable 必须配合 mutex？

`condition_variable` 本身不保存业务条件，它只负责“睡眠”和“唤醒”。

真正的条件在这里：

```cpp
!queue_.empty() || !running_
```

这个条件依赖两个共享状态：

```text
queue_
running_
```

它们必须由同一把 mutex 保护，否则消费者检查条件和生产者修改条件之间可能产生竞态。

正确模型是：

```text
线程 A 持有 mutex，检查 queue_ 是否为空
如果为空，wait 原子地释放 mutex 并睡眠
线程 B 持有同一把 mutex，push 数据
线程 B notify 唤醒线程 A
线程 A 醒来后重新获取 mutex，再检查条件
```

关键点是 `wait` 的“释放锁并进入等待”必须是原子的。否则可能出现：

```text
消费者检查队列为空
生产者 push 并 notify
消费者还没真正进入 wait
消费者开始 wait
通知已经错过，消费者永久睡眠
```

这就是 lost wakeup。

## 4. cv.wait(lock, pred) 内部大致是什么逻辑？

这句：

```cpp
cv_.wait(lock, [this] {
    return !queue_.empty() || !running_;
});
```

大致等价于：

```cpp
while (!pred()) {
    cv_.wait(lock);
}
```

而 `cv_.wait(lock)` 内部会做：

```text
1. 当前线程必须已经持有 mutex
2. 原子地释放 mutex，并让当前线程进入等待队列
3. 当前线程睡眠，不再占用 CPU
4. 被 notify_one / notify_all 唤醒
5. 重新竞争并获取 mutex
6. wait 返回，继续检查谓词
```

注意：被唤醒不代表条件一定满足。

所以必须用谓词，或者手写 `while` 循环检查条件。

## 5. 什么是虚假唤醒？

虚假唤醒是指：

```text
线程从 condition_variable::wait 返回了，
但没有任何业务条件真正满足。
```

也就是说，消费者可能被唤醒，但队列仍然为空。

因此不能写：

```cpp
if (queue_.empty()) {
    cv_.wait(lock);
}
```

因为 `wait` 返回后，条件不一定成立。

应该写：

```cpp
cv_.wait(lock, [this] {
    return !queue_.empty() || !running_;
});
```

或者：

```cpp
while (queue_.empty() && running_) {
    cv_.wait(lock);
}
```

谓词版本更简洁，也更不容易写错。

## 6. 什么是 lost wakeup？

lost wakeup 是指通知发生了，但等待线程没有收到，导致线程可能永久睡眠。

典型错误流程：

```text
消费者检查 queue 为空
生产者 push 数据
生产者 notify
消费者才开始 wait
```

这时通知已经发生过了，消费者之后可能一直睡眠。

使用 `cv.wait(lock, pred)` 能避免这个问题，因为：

```text
检查条件
释放 mutex
进入等待
```

这几个动作在 condition_variable 的协议下被正确组织起来，并且条件状态由同一把 mutex 保护。

更重要的是，即使 notify 先发生，只要条件已经变成 true，消费者之后调用 `wait(lock, pred)` 时也不会睡眠。

## 7. notify_one 和 notify_all 怎么选？

`push()` 时通常使用 `notify_one()`：

```cpp
void push(T value) {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        queue_.push(std::move(value));
    }
    cv_.notify_one();
}
```

因为一次 push 通常只新增一个元素，唤醒一个消费者就够了。

如果使用 `notify_all()`，所有消费者都会被唤醒，但最终通常只有一个消费者拿到数据，其他消费者醒来后发现队列又空了，只能继续睡眠。这会增加不必要的调度开销。

`stop()` 时通常使用 `notify_all()`：

```cpp
void stop() {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        running_ = false;
    }
    cv_.notify_all();
}
```

因为 shutdown 是全局状态变化，所有等待中的消费者都需要醒来检查：

```text
队列里是否还有剩余数据
如果没有数据，是否应该退出
```

所以：

```text
push 一个元素：通常 notify_one
stop 关闭队列：通常 notify_all
```

## 8. notify 应该放在锁内还是锁外？

两种写法在语义上都可以，但常见工程写法是：先修改条件，释放锁，再 notify。

推荐：

```cpp
void push(T value) {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        queue_.push(std::move(value));
    }
    cv_.notify_one();
}
```

原因是：被唤醒的线程醒来后需要重新获取同一把 mutex。如果通知时还持有锁，被唤醒线程可能马上又因为拿不到锁而阻塞。

不过必须注意顺序：

```text
先在 mutex 保护下修改条件
再 notify
```

不要在修改条件之前 notify。

## 9. 当前代码还可以优化的点

第一，`push()` 中建议使用 `notify_one()`。

当前：

```cpp
cv_.notify_all();
```

对于单个元素入队，通常改成：

```cpp
cv_.notify_one();
```

第二，`push()` 和 `pop()` 里不建议在持有队列锁时打印。

当前：

```cpp
std::lock_guard<std::mutex> lock(mutex_);
queue_.push(value);
std::cout << "queue push " << value << "\n";
cv_.notify_all();
```

打印属于 I/O，可能比较慢。持锁打印会拉长临界区，让其他线程等待更久。

更好的做法是：

```cpp
void push(T value) {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        queue_.push(value);
    }
    cv_.notify_one();

    std::cout << "queue push " << value << "\n";
}
```

但多线程打印本身可能交错。如果要保证整行输出不乱，可以使用 C++20 的 `std::osyncstream`：

```cpp
#include <syncstream>

std::osyncstream(std::cout) << "queue push " << value << "\n";
```

或者用单独的打印锁：

```cpp
std::mutex cout_mutex;

{
    std::lock_guard<std::mutex> lock(cout_mutex);
    std::cout << "queue push " << value << "\n";
}
```

第三，`push()` 是否允许在 `stop()` 后继续入队，需要定义清楚。

可以选择：

```text
stop 后禁止 push，push 直接返回 false
stop 后允许 push，但消费者语义要额外说明
```

更常见的是 stop 后禁止 push：

```cpp
bool push(T value) {
    {
        std::lock_guard<std::mutex> lock(mutex_);
        if (!running_) {
            return false;
        }
        queue_.push(std::move(value));
    }
    cv_.notify_one();
    return true;
}
```

第四，`consumer()` 最好根据 `pop()` 的返回值退出，而不是固定 pop 10 次。

当前测试代码知道生产者一定生产 10 个元素，所以固定循环可以跑通。但作为通用消费者，更推荐：

```cpp
void consumer() {
    while (auto value = intBlockingQueue.pop()) {
        std::cout << "consumer pop " << *value << "\n";
    }
}
```

这样消费者和生产者数量解耦，符合 BlockingQueue 的关闭语义。

## 10. 一个更完整的参考实现

```cpp
#include <condition_variable>
#include <mutex>
#include <optional>
#include <queue>

template <typename T>
class BlockingQueue {
public:
    bool push(T value) {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            if (!running_) {
                return false;
            }
            queue_.push(std::move(value));
        }
        cv_.notify_one();
        return true;
    }

    std::optional<T> pop() {
        std::unique_lock<std::mutex> lock(mutex_);
        cv_.wait(lock, [this] {
            return !queue_.empty() || !running_;
        });

        if (queue_.empty()) {
            return std::nullopt;
        }

        T value = std::move(queue_.front());
        queue_.pop();
        return value;
    }

    void stop() {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            running_ = false;
        }
        cv_.notify_all();
    }

private:
    std::queue<T> queue_;
    std::mutex mutex_;
    std::condition_variable cv_;
    bool running_{true};
};
```

这个实现的语义是：

```text
队列运行时，push 成功入队并唤醒一个消费者
队列为空时，pop 阻塞等待
stop 后，所有消费者被唤醒
stop 后，如果还有剩余元素，继续消费
stop 后，如果队列为空，pop 返回 std::nullopt
stop 后，push 返回 false
```

## 11. 面试回答模板

可以这样回答：

```text
BlockingQueue 的核心是用 mutex 保护 queue 和停止标志，用 condition_variable 在队列为空时阻塞消费者。

push 时先持有 mutex 修改 queue，再 notify 唤醒消费者；pop 时使用 unique_lock，因为 condition_variable::wait 需要在等待时释放 mutex，被唤醒后再重新获取 mutex。

wait 必须配合谓词，例如 queue 非空或已经 stop。谓词可以处理虚假唤醒，也能避免 notify 先发生导致的 lost wakeup。

stop 时要在 mutex 保护下修改停止标志，然后 notify_all 唤醒所有消费者。因为 shutdown 是全局状态变化，所有等待线程都应该醒来判断是否退出。

push 一个元素通常 notify_one 即可，stop 时通常 notify_all。

stop 后的语义要说清楚：我的设计是继续消费队列中剩余元素；当队列为空且已经 stop 时，pop 返回 std::nullopt，消费者据此退出。
```

# 第 4 题：死锁

## 1. 为什么可能产生死锁？

题目中的两个线程：

```text
线程 A:
lock(mutex1)
lock(mutex2)

线程 B:
lock(mutex2)
lock(mutex1)
```

可能出现这样的执行顺序：

```text
线程 A 成功锁住 mutex1
线程 B 成功锁住 mutex2
线程 A 继续尝试锁 mutex2，但 mutex2 被线程 B 持有，所以 A 阻塞
线程 B 继续尝试锁 mutex1，但 mutex1 被线程 A 持有，所以 B 阻塞
```

结果是：

```text
线程 A 持有 mutex1，等待 mutex2
线程 B 持有 mutex2，等待 mutex1
```

两个线程都在等待对方释放锁，但它们自己又不会继续执行到释放锁的位置，于是形成死锁。

死锁的本质是：多个线程之间形成了环形等待关系，每个线程都持有别人需要的资源，同时又等待别人释放资源。

## 2. 死锁形成的四个必要条件

死锁通常需要同时满足四个条件：

```text
互斥条件
持有并等待
不可抢占
循环等待
```

第一，互斥条件。

资源一次只能被一个线程持有。例如一个 `mutex` 被线程 A 锁住后，线程 B 不能同时持有同一把锁。

第二，持有并等待。

线程已经持有了一部分资源，同时还在等待新的资源。

例如：

```text
线程 A 已经持有 mutex1，又等待 mutex2
线程 B 已经持有 mutex2，又等待 mutex1
```

第三，不可抢占。

线程持有的锁不能被其他线程强制夺走，只能由持锁线程主动释放。

第四，循环等待。

线程之间形成一个等待环：

```text
线程 A 等线程 B 的资源
线程 B 等线程 A 的资源
```

更复杂时可能是：

```text
A 等 B
B 等 C
C 等 A
```

只要破坏这四个条件中的任意一个，就可以避免死锁。

## 3. 解决办法一：固定加锁顺序

最常用的工程方法是制定固定的 lock ordering。

例如规定：

```text
所有线程必须先锁 mutex1，再锁 mutex2
```

那么线程 A 和线程 B 都这样写：

```cpp
std::lock_guard<std::mutex> lock1(mutex1);
std::lock_guard<std::mutex> lock2(mutex2);
```

这样就不会出现：

```text
线程 A 持有 mutex1 等 mutex2
线程 B 持有 mutex2 等 mutex1
```

因为线程 B 如果也必须先锁 `mutex1`，它会在第一步就阻塞，不可能先拿到 `mutex2`。

固定加锁顺序本质上是破坏死锁四条件中的“循环等待”。

## 4. 解决办法二：std::scoped_lock

C++17 提供了 `std::scoped_lock`，可以一次性锁住多个 mutex：

```cpp
std::mutex m1;
std::mutex m2;

void work() {
    std::scoped_lock lock(m1, m2);
    // 同时持有 m1 和 m2
}
```

`std::scoped_lock(m1, m2)` 的意义是：

```text
用 RAII 管理多个锁的生命周期
用标准库内部的死锁避免算法获取多个锁
离开作用域时自动释放所有锁
```

它比手写：

```cpp
m1.lock();
m2.lock();
```

更安全。

手写多个 `lock()` 有两个问题：

```text
不同线程可能加锁顺序不一致，导致死锁
中途抛异常时，已经获取的锁可能无法释放
```

`std::scoped_lock` 同时解决了锁顺序和 RAII 释放问题。

## 5. 解决办法三：std::lock + adopt_lock

在 C++17 之前，也可以使用 `std::lock` 一次性获取多个锁：

```cpp
std::lock(m1, m2);
std::lock_guard<std::mutex> lock1(m1, std::adopt_lock);
std::lock_guard<std::mutex> lock2(m2, std::adopt_lock);
```

这里：

```text
std::lock(m1, m2) 负责以避免死锁的方式获取多把锁
std::adopt_lock 表示这把锁已经被当前线程持有
lock_guard 后续只负责析构时 unlock
```

注意：使用 `adopt_lock` 的前提是当前线程已经持有这把锁。否则就是错误用法。

C++17 以后，能用 `std::scoped_lock` 时通常优先用它：

```cpp
std::scoped_lock lock(m1, m2);
```

## 6. 解决办法四：缩小临界区

不要在持锁期间做耗时或不可控操作。

应该避免在持锁时执行：

```text
网络 I/O
磁盘 I/O
sleep
复杂计算
调用未知外部回调
等待其他线程
```

错误倾向：

```cpp
std::lock_guard<std::mutex> lock(m);
readFromNetwork();
updateSharedState();
```

更好的思路：

```cpp
auto data = readFromNetwork();

{
    std::lock_guard<std::mutex> lock(m);
    updateSharedState(data);
}
```

缩小临界区不能从根本上证明没有死锁，但它能减少锁持有时间，降低死锁和性能问题出现的概率。

## 7. 解决办法五：避免嵌套锁或分阶段释放

如果业务允许，尽量不要同时持有多把锁。

例如可以把数据复制出来后释放第一把锁，再去获取第二把锁：

```cpp
Data snapshot;
{
    std::lock_guard<std::mutex> lock(m1);
    snapshot = data1;
}

{
    std::lock_guard<std::mutex> lock(m2);
    updateData2(snapshot);
}
```

这种方式通过减少“持有一把锁时等待另一把锁”的情况，破坏“持有并等待”条件。

但要注意：释放锁后数据可能被其他线程修改，所以这种做法必须确认业务语义允许使用快照。

## 8. 如果必须分阶段获取锁，如何制定 lock ordering？

工程中如果无法避免多个锁，就要给锁建立全局顺序。

例如：

```text
Account mutex 按 account_id 从小到大加锁
Node mutex 按内存地址从小到大加锁
模块级锁先于对象级锁
全局锁先于局部锁
父节点锁先于子节点锁
```

转账场景：

```cpp
void transfer(Account& from, Account& to, int amount) {
    Account* first = &from;
    Account* second = &to;

    if (second->id < first->id) {
        std::swap(first, second);
    }

    std::scoped_lock lock(first->mutex, second->mutex);

    from.balance -= amount;
    to.balance += amount;
}
```

这里即使业务上是 `from -> to`，加锁顺序也不按业务方向，而是按稳定的全局规则，例如 `account_id` 从小到大。

制定 lock ordering 时要注意：

```text
顺序必须全局统一，不能只在单个函数里统一
顺序依据必须稳定，例如 id、层级、地址
代码评审时要检查是否违反锁顺序
文档中要明确哪些锁可以嵌套，以及嵌套顺序
```

## 9. try_lock 和超时锁

有时也可以用 `try_lock()` 避免永久等待。

例如：

```cpp
if (m.try_lock()) {
    std::lock_guard<std::mutex> lock(m, std::adopt_lock);
    doWork();
} else {
    // 获取失败，放弃或稍后重试
}
```

对于 `std::timed_mutex`，还可以使用超时等待：

```cpp
if (m.try_lock_for(std::chrono::milliseconds(100))) {
    std::lock_guard<std::timed_mutex> lock(m, std::adopt_lock);
    doWork();
}
```

这类方式可以避免线程永久卡死，但它们通常不能替代清晰的锁顺序设计。因为失败重试、回滚和业务一致性也会增加复杂度。

## 10. 如何排查死锁？

工程中排查死锁可以从几个方向入手：

```text
观察线程栈，看线程卡在哪些 mutex lock 上
检查每个线程已经持有哪些锁、正在等待哪些锁
寻找 A 等 B、B 等 A 的循环等待关系
检查是否有裸 lock 后异常或提前 return 未 unlock
检查是否在持锁时调用外部回调或阻塞 I/O
```

Linux 下可以结合：

```text
gdb 查看所有线程栈
pstack / eu-stack
日志记录 lock/unlock 顺序
ThreadSanitizer 辅助发现部分锁顺序问题
```

面试中不用展开工具细节，但可以提一句：死锁排查重点是看线程等待关系和锁获取顺序。

## 11. 面试回答模板

可以这样回答：

```text
这段代码可能死锁，因为线程 A 先持有 mutex1 再等待 mutex2，而线程 B 先持有 mutex2 再等待 mutex1，两个线程互相等待对方释放资源，形成循环等待。

死锁形成通常需要四个条件：互斥、持有并等待、不可抢占、循环等待。避免死锁的核心就是破坏其中至少一个条件，工程中最常见的是破坏循环等待。

解决办法包括：制定固定加锁顺序，所有线程按同一顺序获取锁；使用 std::scoped_lock 一次性获取多把锁；使用 std::lock + adopt_lock；缩小临界区，避免持锁做 I/O、sleep 或调用外部回调；必要时用 try_lock 或超时锁避免永久等待。

std::scoped_lock(m1, m2) 的意义是用 RAII 管理多把锁，并使用标准库的死锁避免算法获取多个 mutex，离开作用域时自动释放。

如果业务必须分阶段获取锁，就要制定全局 lock ordering，例如按对象 id、层级或地址排序。这个顺序必须全局一致，不能在不同函数里各自定义，否则仍然可能形成循环等待。
```
